## PPO 实现：用 TRL 跑一遍

前面讲过 PPO 的损失和四个模型。真到写代码的时候，问题会变成一堆具体的接口。

这一章用 TRL 走一遍。目标不是训出好模型，是把流程跑通，知道每个旋钮在哪。

版本先说清楚。下面按 TRL 零点九到零点十二这一代的接口写。之后的版本把采样和训练拆成了两套组件，名字变了，概念没变。

### 四个模型在代码里怎么摆

策略模型和参考模型都是语言模型，价值模型是策略模型加一个标量头。TRL 里用 `AutoModelForCausalLMWithValueHead` 一次拿到，它在语言模型的输出上加了一个 `value_head`。

配置集中在一个对象里。

```python
from trl import PPOConfig, PPOTrainer, AutoModelForCausalLMWithValueHead

cfg = PPOConfig(
    learning_rate=1.41e-5,
    batch_size=64,
    mini_batch_size=8,
    ppo_epochs=4,
    init_kl_coef=0.05,
    target_kl=6.0,
    adap_kl_ctrl=True,
    cliprange=0.2,
    cliprange_value=0.2,
    gamma=1.0,
    lam=0.95,
)
```

几个参数值得单独说。

`batch_size` 是一次采样多少条回答。`mini_batch_size` 是把这批拆成几份做梯度更新，两者的比值决定了每批数据被复用几次。

`ppo_epochs` 是复用轮数。语言模型的 PPO 通常只跑二到四轮，再多就会过拟合这一批数据，重要性采样比也会跑出裁剪区间。

`init_kl_coef` 和 `target_kl` 配 `adap_kl_ctrl` 用。KL 超过目标就调大系数，低于目标就调小。这比手写一个固定系数稳，因为最优的 KL 强度会随训练阶段变化。

`gamma` 和 `lam` 在这个场景里通常设成 1.0 和 0.95。语言模型的回合很短，折扣的意义不大，很多人直接把整段回报当优势。

模型装进来只要几行。

```python
policy = AutoModelForCausalLMWithValueHead.from_pretrained(
    name, load_in_8bit=True)
ref = AutoModelForCausalLMWithValueHead.from_pretrained(
    name, load_in_8bit=True)
trainer = PPOTrainer(config=cfg, model=policy,
                     ref_model=ref, tokenizer=tok)
```

参考模型加载完就冻结。它的参数不参与更新，只提供对数概率。

价值头的初始化影响不小。默认的随机初始化意味着前几十步的优势估计基本是噪声，策略在噪声上更新，很容易一开始就跑偏。一个实用的做法是先把学习率调小，等价值损失降下来再放大，或者干脆用规则奖励先跑一小段。

奖励的归一化也要考虑。不同批次的奖励分布会漂，如果把原始分数直接喂进 PPO，优势的尺度会跳。常见的处理是在一批内部减去均值再除以标准差，注意这只能批内做，不能跨批平滑，否则会把历史信息带进来。

### 一批数据在四个模型之间怎么走

把一次 `step` 拆开，能看出钱花在哪里。

第一批是采样。策略模型对每道题生成若干条回答，这一步是串行的，一条接一条出 token，GPU 利用率很低。

第二批是打分。奖励模型对每条回答跑一次前向，只取最后一个位置的输出。这一步可以批处理，成本比采样低得多。如果奖励是规则函数，成本几乎为零。

第三批是两次前向。策略模型重新算一遍回答的对数概率，参考模型也算一遍。两份都要，前者算重要性采样比，后者算 KL。

第四批是价值头。它挂在策略模型的输出上，和第三批共用一次前向，不额外花时间。这也是把它和策略绑在一个模型里的原因。

最后才是更新。把上面算出的优势、比值、KL 拼起来，做几轮小批量梯度下降。

四批里只有第一批真正贵。所以优化的重点总在生成上，而不是在损失函数上。一个常见的误判是花一周调 PPO 的超参，而采样引擎换一下能快三倍。

### reward function 写什么

PPO 本身不关心奖励从哪来。`trainer.step` 收一个浮点数列表，剩下的它不管。

这意味着奖励函数是唯一需要自己设计的部分。常见组合是这样。

```python
def reward_fn(prompt, response):
    score = 0.0
    score += 1.0 if answer_matches(prompt, response) else 0.0
    score += 0.2 if has_reasoning_block(response) else 0.0
    score -= 0.001 * num_tokens(response)       # soft length penalty
    score -= 1.0 if repeats(response) else 0.0
    return score
```

三条经验。

奖励的调用方式值得单独设计。奖励模型通常是另一个模型，每步要为几十条回答打分，这部分开销经常被低估。能批处理的就批处理，能在生成时同步算的不要留到最后。

奖励要稀疏得合理。全给零，学不到东西。全是小分数，模型会去优化那些容易拿的分，比如格式分，而不是正确率。

量纲要统一。规则分的范围要清楚，别让某一项压过其他所有项。奖励模型输出的分数通常要做标准化，否则不同版本之间不可比。

长度项必须有。哪怕只减一个很小的系数，也能压住回答变长的趋势。这不是可选项，因为奖励模型和规则分都天然偏好长回答。

混合奖励时要定一个比例。规则分和奖励模型分放在一起，容易出现一个问题，模型很快学会把规则分拿满，然后不再关心奖励模型那部分。处理办法是把规则分设成必要条件，不满就归零，满足才给奖励模型的分数，而不是把两者相加。

### 奖励函数的三种写法

同一个奖励，写法不同，效率差很多。

第一种是逐条调用。最简单，也最慢。奖励模型每条单独跑一次前向，批大小为一，一张卡只能用到很小一部分算力。只在调试时用。

第二种是批处理。把所有回答拼成一批，一次前向算完。代码不长，收益很大。

```python
import torch

def batched_reward(responses, rm, tok, max_len=2048, bs=32):
    # score all responses in chunks, no grad needed for the reward model
    out = []
    for i in range(0, len(responses), bs):
        chunk = responses[i:i + bs]
        enc = tok(chunk, padding=True, truncation=True,
                  max_length=max_len, return_tensors="pt")
        with torch.no_grad():
            out.extend(rm(**enc).logits.squeeze(-1).float().tolist())
    return out
```

注意那个 `float()`。分数最后要参与优势计算，半精度的微小差值会在后面放大。

第三种是带门控的。先用便宜的规则判一道，不达标就直接给最低分，达标才调贵的奖励模型。这能把奖励模型的调用量降一个量级，因为大部分回答在格式这一关就被拦下了。

```python
def gated_reward(response, rm_score):
    # cheap checks first, expensive model only when they pass
    if not has_answer_tag(response):
        return -1.0
    if is_repetitive(response):
        return -0.5
    return rm_score
```

门控的顺序有讲究。先查那些一旦不过就不该继续算的项，再算贵的那一部分。顺序反了，性能优化白做。

还有两件工程上的事。一是奖励函数要能容错，某条回答让验证器抛异常时，不能把整批打断，应该给它一个默认分并记一条日志。二是奖励函数要能超时，代码类任务的验证器可能卡死，卡住的代价是整条训练循环停下来等。

### 主循环：采样、打分、更新

训练循环的形状很朴素。

```python
for batch in loader:
    qs = [tok(p, return_tensors="pt").input_ids.to(dev)
          for p in batch["prompt"]]
    rs = [trainer.generate(q, max_new_tokens=256,
                           do_sample=True, top_p=0.95)[0]
          for q in qs]
    scores = [reward_fn(p, tok.decode(r))
              for p, r in zip(batch["prompt"], rs)]
    stats = trainer.step(qs, rs, scores)
```

`trainer.generate` 返回的是新生成的 token，不含问题部分。这一点在版本之间有过变化，有的版本返回拼接后的整段。接错会导致掩码全错，训练看起来在跑，其实什么也没学到。

`stats` 里有几项要盯。

`ppo/mean_scores` 和 `ppo/returns/mean` 应该缓慢上升。`ppo/policy/approxkl` 应该在零点零几的量级，突然跳到零点几说明更新太猛。`ppo/policy/entropy` 缓慢下降是正常的，掉得太快说明模型已经收敛到少数回答上。

还有一个不在 `stats` 里但更重要的指标，回答长度。它如果一路上涨而分数没动，说明模型在钻长度的空子。

### 从 stats 里读问题

指标不是用来看趋势的，是用来定位故障的。几个常见组合。

奖励涨、KL 也涨、长度涨。这是典型的奖励黑客前兆。模型在把一个和真实质量无关的特征放大。先查奖励里有没有长度项，再查奖励模型是不是被某种格式骗了。

奖励涨、KL 稳、熵崩。模型找到了一个能拿分的固定句式，多样性在死。加熵奖励，或者混入一部分监督数据。

奖励不涨、KL 也不涨。两个可能，要么奖励全是零，模型根本没学会；要么重要性采样比已经被裁死，梯度传不进去。看裁剪比例这个统计项就能分开。

:::

### 两处掩码与 KL 的位置

PPO 在语言模型上有两处容易写错，都和掩码有关。

第一处是损失只算回答部分。问题部分的 token 是给定的，模型不该为它负责。实现上要把问题长度之前的位置全部置零。

第二处是 KL。TRL 的默认做法是把 KL 加进奖励，逐 token 加。

$$
r_t = r^{\text{total}} - \beta\,\mathrm{KL}_t,\qquad
\mathrm{KL}_t = \exp\left(\log\pi_\theta - \log\pi_{\text{ref}}\right) - \left(\log\pi_\theta - \log\pi_{\text{ref}}\right) - 1
$$

这个形式叫 k3 估计，恒非负，方差比直接算对数比小。有的实现用 k1，也就是直接取对数比，可以为负，训练早期波动更大。

加进奖励之后，重要性采样比也要逐 token 算。

$$
\rho_t = \frac{\pi_\theta(y_t\mid x,y_{<t})}{\pi_{\theta_{\text{old}}}(y_t\mid x,y_{<t})}
$$

分母是采样时的策略，不是参考模型。这两者经常被混淆。参考模型只用来算 KL，旧策略只用来算比值。

还有一处细节是优势的算法。TRL 默认用 GAE，逐个 token 算。语言模型里每条回答只有一个奖励，GAE 退化成把同一个优势分配给后面的每个 token，越靠后的 token 权重越高。这恰好符合直觉，靠近结尾的 token 对最终分数负责更多。

有人试过改为按整段平均分配，效果通常更差。也有人干脆不用价值头，直接用整段分数减组均值，那就是 GRPO 的做法。

一处写错，训练不会立刻报错，只会慢慢变差。所以第一版实现最好在一个小任务上验证，确认分数能涨上去，再换大模型。

### 三个超参的相互影响

PPO 的超参不能一个一个调，它们互相影响。

学习率和批大小是一对。小的批加上大的学习率，梯度噪声大，模型会在奖励面上跳来跳去，表现出来就是奖励曲线毛刺很多。反过来，大的批加上小的学习率，稳定但慢，而且容易停在平坦区域。常见的起点是学习率在一点几乘十的负五次这个量级，批大小六十四，比单卡默认值大一些。

复用轮数和批大小也是一对。同一批数据跑四轮，等于把这批数据的学习率乘以四。批越大，复用带来的偏差越小，因为数据多样性多。批小的时候，第三轮开始基本就在背这几条回答，重要性采样比也会跑出裁剪区。

KL 系数和奖励尺度是一对。奖励的方差大，KL 的效果就弱，因为梯度被奖励主导。所以换奖励的时候要重新看 KL，不能沿用上一个任务的系数。自适应 KL 能缓这一块，但它靠目标值 $\text{target\_kl}$ 说话，那个数设错了，自适应也救不了。

还有一个不常被当成超参的东西，温度。采样温度高，回答多样但质量下降，奖励均值低、方差大。温度低，回答集中，奖励均值高但组内没有区分度。在多轮任务里这一点更明显，温度低到一定程度，一组八条轨迹几乎一样，优势全为零。

调试时一次只改一个。同时改两个超参，看到一个变化也不知道是谁带来的。这条建议很老套，但在 PPO 里比在监督学习里重要，因为它本来就不稳定，噪声比信号大。

### 采样与训练的配比

在线训练里有一个绕不开的比例，采样用多少卡，训练用多少卡。

生成是自回归的，一条两千 token 的回答要跑两千次前向，每次只出一个 token。训练是一次前向过整段，并行度高。两者每 token 的实际耗时差一两个数量级，具体看模型大小、批大小和引擎优化。

这个差距造成一个局面，采样吞吐决定整个训练的速度。做法通常是把生成放到单独的推理引擎上，用张量并行和多卡并行把吞吐拉起来，训练侧只有少数卡在等数据。有的实现把采样和训练放在同一组卡上分时复用，省显存但速度略低。

还有一个副作用叫策略陈旧。采样和训练不同步，采样时用的是旧权重，训练时用的是新权重。间隔越大，重要性采样比越偏离一，裁剪就越频繁，有效样本越少。

处理办法有两个。一是频繁同步权重，每几十步把新权重推给采样引擎一次。二是把陈旧度当成参数记下来，日志里存着这条数据是用差多少步的权重采的，出问题时能对得上。

后者常被忽略，但它是排查训练前期正常、后期不动这类问题的关键线索。如果日志里没有这个字段，只能猜。

### 显存、算力与流程验证

显存账要先算清楚。一个七 B 模型半精度约十四 GB，策略加参考就是二十八 GB，加上价值头、优化器状态和激活，单卡八十 GB 都紧张。

### 显存账怎么算

把每一项拆开，数字就清楚了。

参数。七 B 乘两字节，十四 GB。

梯度。和参数同尺寸，再十四 GB。

优化器状态。Adam 要两份矩估计，用 fp32 存，就是七 B 乘四字节乘二，五十六 GB。如果再保留一份 fp32 主权重，再加二十八 GB。

四项加起来一百一十二 GB。还没算激活，已经超过一张八十 GB 的卡。这就是为什么全参 PPO 在七 B 上不现实。

激活的量级可以这样估。层数乘批大小乘序列长度乘隐藏维度乘两字节，再乘一个系数。系数取决于存了多少中间张量，常见在十上下。三十二层、批八、序列一千零二十四、隐藏四千零九十六，算出来是二十一 GB 左右。序列长度翻倍，它翻倍。

所以显存的真实组成是，优化器状态最大，激活第二，参数和梯度反而小。只看参数量去估显存，会低估一倍以上。

省法的性价比排序如下。

量化参考模型。参考模型只做前向，八 bit 甚至四 bit 都够用，精度损失对 KL 的影响很小。

把参考模型和奖励模型放到 CPU 或者另一张卡上，按需调用。速度会慢，但显存省下来了。

只训 LoRA。策略模型冻结，只训低秩适配器，优化器状态从几十 GB 降到几百 MB。代价是学习能力受限，长链推理这类任务上效果会打折。

开梯度检查点。用时间换显存，激活值重算一遍，显存能省一半左右，速度慢两成。

采样交给推理引擎。生成是瓶颈，用 vLLM 之类做采样能快好几倍。新版 TRL 支持把生成和训练分开，这是目前最实用的改法。

这几条可以叠加。一个务实的组合是，策略用 LoRA 加梯度检查点，参考模型八 bit 放同一张卡，生成走推理引擎。

### 流程验证怎么做

实在没有算力，大模型跑不动，不代表不能验证实现。

第一步，把奖励换成一个完全确定的规则。比如让模型算三个两位数相加，答案用固定格式输出。规则奖励只看格式和数值，没有奖励模型的噪声。

第二步，选一个零点五 B 级别的模型。它的能力刚好够学会这个任务，又小到单卡能跑。

第三步，只跑几百步。看四件事，奖励是否上升，KL 是否稳定在小范围，回答长度是否失控，随机抽十条看格式是否合规。

四项里只要有一项不对，先修实现，别急着换大模型。经验上，第一次实现 PPO 出的问题九成在这四项里。

第四步，把规则奖励换成一个小的奖励模型，再看一遍。如果分数不涨了，问题在奖励模型；如果涨得很快然后崩，问题在 KL 或者长度控制。

这套流程两天能走完，比在七十 B 上试错省得多。

还有一件事要在小任务上顺手确认，就是可复现。固定种子、固定数据顺序、固定采样参数，跑两次看曲线像不像。不像的话，先查数据加载有没有并行乱序，再查采样有没有用到非确定性的内核。这一项不确认，后面所有对比都不可信。

配置也要存。批大小、学习率、KL 系数、长度上限、模型哈希、数据版本，全部写进一个文件，和检查点放在一起。一周后回头查一个异常，靠的就是这份记录。靠记忆和聊天记录找参数，是很多团队隐形的成本。

### 分布式怎么切

单卡装不下时，要选一种切法。三种常见。

数据并行。每张卡一份完整模型，分不同的数据。它不省显存，只提吞吐，适合模型能装进单卡的场景。

ZeRO 式的分片。把优化器状态、梯度、参数依次切开，分到各卡上。第一阶段只切优化器状态，第二阶段加梯度，第三阶段加参数。切得越深，显存省得越多，通信越贵。七 B 模型上切到第二阶段通常够用。

张量并行。把一层内部的矩阵切开，适合单层就装不下的超大模型。通信最频繁，需要高速互联。

选哪种看瓶颈在哪里。显存不够但单卡算得动，用分片。单卡装不下也切不开，用张量并行。两个都不是问题，只是想快，用数据并行。

还有一个在 PPO 里特有的麻烦，四个模型不一定用同一种切法。常见配置是策略和价值用分片，参考模型量化后放单卡，奖励模型放 CPU。这种混合配置能跑，但调试成本高，每一步要确认张量在不在正确的设备上。第一版实现建议全放一张卡，先保证能跑通。
