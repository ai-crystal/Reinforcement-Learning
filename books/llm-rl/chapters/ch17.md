## 可验证奖励的数据工程

算法定下来之后，同样一套 GRPO，两个人跑出来的结果能差十几个点。差别几乎都在数据上。

可验证奖励听起来很干净，答案对就一分，错就零分。但"答案对不对"这件事，取决于怎么抽取、怎么比对、题目本身难不难。这一章讲这几件事。

### 难度与课程

奖励只有零和一，一组回答全对或者全错时，组内没有区分度。

用 GRPO 的话说，优势是组内标准化的结果。

$$
A_i = \frac{r_i - \mathrm{mean}(r_{1:G})}{\mathrm{std}(r_{1:G}) + \epsilon}
$$

全对时分子全为零，全错时也一样，梯度也是零。这一批数据白采了。

所以题目要筛。做法是维护每道题的通过率估计 $\hat p$，采样时优先取 $\hat p$ 落在中间的那些。太简单的题，模型每次都做对，学不到东西。太难的题，模型一次都做不对，也学不到东西。

中间区间取多宽，取决于组大小。组大小是八时，如果单条通过率是零点九，一组全对的概率接近零点四十三；如果是零点五，全对的概率只有千分之四。所以通过率高的题要更多样本才能挤出信号，这也是筛题的价值。

通过率从哪来。最省事的办法是先跑一遍，用当前模型对每题采若干条，统计正确率。这一遍的生成量不小，但可以在训练开始前一次性做完，之后每隔一段时间更新。

课程有两种排法。

按难度递增。先用通过率高的题让模型上手，格式稳定之后再换难题。好处是早期就有正样本，训练曲线好看。坏处是模型可能先学会一套只在简单题上有效的模板。

按通过率加权采样。不排序，每道题被抽到的概率和它离中间区的距离成反比。这更接近自适应，实现也简单。

两种做法都能用，第一种更好调。要注意的是难度会随训练变化，一开始很难的题，两周后可能变成简单题。课程表要跟着重算，不能一次定死。

题目来源也要看。从竞赛题、教辅、合成题里各取一部分，难度分布和风格都不同。合成题好控难度，但容易不自然，模型学到的可能是合成模板。竞赛题质量高，数量少，很容易被模型记住。三类混着用，并按来源分别统计通过率，才能看出模型是真的变强了，还是在适应某一类题。

### 答案抽取

模型输出一整段推理，程序要从中找到答案。这一步看着琐碎，是坏数据的主要来源之一。

办法是约定格式。推理过程放在固定标记之间，最后一行用固定前缀给出答案。训练时用提示模板强制这个格式，抽取时用正则找。

```python
import re

BOXED = re.compile(r"\\boxed\{([^{}]*)\}")
LAST_LINE = re.compile(r"####\s*([^\n]+)")

def extract(text):
    hits = BOXED.findall(text)
    if hits:
        return hits[-1].strip()
    m = LAST_LINE.search(text)
    if m:
        return m.group(1).strip()
    return None
```

三个细节。

取最后一个匹配，不取第一个。模型有时会在推理中途写一个临时的 boxed，最后再给最终答案。取第一个会大面积判错。

抽取失败必须单独统计。一个健康的训练集，抽取失败率应该在百分之一以下。如果到了百分之十，说明格式没训好，这时候奖励信号里有十分之一是假阴性，等于给正确回答发零分。这种噪声比随机噪声更糟，因为它系统性地惩罚了正确的行为。

模型的输出会被截断。达到最大长度时，答案可能还没写出来。这类样本要单独标记，不要混进错题里。

### 验证器

抽出答案之后要判断它和标准答案是否等价。字符串直接比会错得很离谱。

分数要通分，小数和分数要能互认。表达式要能化简，$2\sqrt{2}$ 和 $\sqrt{8}$ 是同一个数。单位要能省略，空格和标点要忽略。集合类的答案要能与顺序无关。

```python
from sympy import simplify, sympify
from sympy.parsing.sympy_parser import parse_expr

def canon(s):
    return s.strip().replace(" ", "").replace(",", "").lower()

def equal(pred, gold, tol=1e-6):
    if pred is None:
        return False
    if canon(pred) == canon(gold):
        return True
    try:
        return abs(float(sympify(pred) - sympify(gold))) < tol
    except Exception:
        pass
    try:
        return simplify(parse_expr(pred) - parse_expr(gold)) == 0
    except Exception:
        return False
```

这段代码不算完美，但覆盖了大部分情况。要注意的是 `sympify` 会执行表达式，训练数据来自不可信的模型输出，做大规模训练时应该放在受限的解释器里跑，或者用符号解析器而不是求值器。

验证器要往两个方向测。拿一批标准答案，故意改写成等价形式，看是否判对。再拿一批错误答案，看是否判错。两个测试集都要有，只测一边会调出偏保守或者偏宽松的验证器。

偏保守的后果是正确回答被判错，模型学到的是别写复杂表达式。偏宽松的后果是错误回答被判对，模型学会的是凑形式。后者的破坏更大，因为它会直接导致奖励黑客。

还有一类任务没有标准答案，只有测试用例。这类任务的验证器就是跑代码，风险也更高，因为代码可以读环境、可以改文件。训练时的沙箱必须真的隔离，网络、文件系统、进程都要限制。这不是安全讲究，是防止几千个进程同时把机器跑死。

### 测试用例

代码任务的验证器是单元测试。这里的工程问题更多。

测试要分公开和隐藏。公开的给模型看，帮它理解要求。隐藏的用来判分，防止它针对测试写死代码。

测试要覆盖边界。空输入、超长输入、重复元素、负数、越界。模型写的代码经常在主路径上正确，边界上崩溃。

测试不能 flaky。涉及随机、时间、浮点的用例要做确定性处理，否则同一份代码跑两次结果不同，奖励就不稳定。发现 flaky 用例要立刻删掉，不要指望用重试掩盖。

测试不能太少。三个用例的题，模型写个特判就能过。一道题至少要有覆盖主要分支的若干用例，具体数目看任务复杂度。

测试也不能太严。要求输出格式一字不差，会把正确但格式略有差异的解判错。除非格式本身是任务的一部分，否则应该放宽。

### 长度、去重与污染

长度要控。奖励只看对错时，模型有明确的动机写得更长，因为长推理碰巧对的概率更高。这是有代价的，推理成本上去，延迟变长，可读性下降。

处理办法是在奖励里减一个长度项，或者按长度分桶统计正确率。后者的信息量更大，能看出模型是不是只在长回答上正确。

去重容易被忽略。题库来自多个来源，同一道题换个数字、换个说法就会出现好几次。近似重复的题会让模型过度拟合那个题型，也会让通过率估计失真。做法是用 n-gram 或 MinHash 做近似去重，相似度超过阈值只留一条。

污染检查是另一回事。训练题库里如果混进了评测集的题，评测分数就不可信。检查办法是拿训练题和评测题做片段匹配，命中的删掉。还要注意改写的题，题面不同但解法完全一样，这类只能靠人工抽查。
