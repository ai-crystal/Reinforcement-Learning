## 对齐的代价：谄媚、退化与多样性

第 11 章末尾说，多轮任务的评估比单轮复杂得多。在谈评估之前，先看一件更容易被跳过的事。

对齐训练不是只加不减。它一边提升模型在目标上的表现，一边拿走一些东西。拿走了什么，往往要等到上线之后才被发现。

### 对齐税

做完偏好训练的模型，经常在通用基准上比监督微调的版本差一点。数学题掉两三个点，代码能跑的比例下降，写故事时用词变得保守。这个现象有个名字，叫对齐税。

具体数字因项目而异，方向却相当稳定。原因有几层。

偏好数据偏向安全、礼貌、结构化的回答。模型为了提高奖励，会把输出分布往这个方向收窄。收窄的过程里，那些不常见但有创造力的表达被压掉。

奖励模型本身有偏，模型学会了讨好它，而不是学会变得更有用。

信用分配太粗。整段回答只有一个分数，一些本来正确的 token 也被连带惩罚。

KL 约束只是限制幅度，不改变方向。它让模型别走太远，走的方向仍然是奖励指的方向。

观测的办法不复杂。训练前后在同一个基准、同一个提示模板、同一个采样温度上各跑一遍，比较的不只是目标指标，还有几项与目标无关的通用能力。数学、代码、长文写作，各留一条。很多团队只盯目标指标，等上线才发现模型在别的地方变笨了。

模型越小，这一项越明显。七 B 级别的模型做一轮偏好训练，通用能力的损失往往大于百 B 级别。原因不难想，小模型的容量刚好够装下预训练学到的东西，对齐训练挤进来一部分，就得挤出去一部分。

还有一点容易被忽略。对齐税不是训练结束就固定的。上线之后继续用新数据做增量训练，每一轮都会再收窄一点。几轮下来，模型可能变得很听话，也很平庸。

### 对齐税怎么量成一个数

要报一个数，得先定义清楚比什么。做法是配对的，把训练前后的模型放在同一套探针上跑。

探针要覆盖两件事。一是目标能力，训练就是为了提升它，它得涨。二是无关能力，训练不该碰它，它掉了才是税。第二类探针最容易被忽略，因为没人会主动去测一个和训练目标无关的东西。

具体操作有几条。

固定提示模板，固定采样温度为零，固定最大长度。同一个脚本跑两个模型，逐题对比，只统计两边都能解析出答案的题。解析失败的比例单独报，它本身就是个信号。一边解析成功率是百分之九十八，另一边掉到百分之九十，这八个点里藏着格式退化。

算差值，不算绝对值。绝对值受提示模板影响很大，差值稳定得多。同一个模型换个模板，绝对分能差三到五个点，差值通常只差一个点以内。

差值要带区间。几百道题上的准确率，标准误大约两个百分点，两个模型各一点几，差值的不确定性就有三到四个点。所以看到掉一个点，不能叫税，那在噪声里。掉五个点以上才值得讨论。

这几句话看着琐碎，却是这一章最实用的一段。很多团队报的对齐税，其实就是采样噪声。换一个种子，符号就变了。

还有一件要提前定的事，用哪个检查点。用最后一轮的，还是验证集上最好的。这两个不是同一个模型，通用能力的损失也不一样。最后一轮通常掉得更多，因为模型在目标上跑得更远。对外报数字时要把这个说清楚，否则两篇报告的数字无法对齐。

除了准确率，还有两个便宜的信号值得存下来。一是平均输出长度，它提前预告了长度偏置。二是回答里出现公式、代码块、列表的比例，这三项的占比在偏好训练后几乎总是上升，上到多少算病态，得自己定一个阈值。

### 谄媚

用户说错，模型跟着错。用户说我觉得答案是 B，模型立刻改口。用户语气强硬，模型放弃原来的判断。

这是偏好训练最稳定的副作用之一。

来源很清楚。偏好数据里，附和用户的回答更容易被选中。标注者是人，人也喜欢被认同。这不是标注者不认真，是比较这种形式本身的局限。它只记录哪个更让人舒服，不记录哪个更正确。

检测可以很简单。取一批有确定答案的题，在原问题后面加一句带错误主张的用户意见，看模型是否改口。

```python
def flip_rate(ask, judge, items, pressure):
    """Ask each question twice: plain, then with a wrong user claim."""
    flipped = 0
    for question, gold in items:
        first = ask(question)
        claim = wrong_claim(gold)
        second = ask(question + pressure.format(claim=claim))
        if judge(first, gold) and not judge(second, gold):
            flipped += 1
    return flipped / len(items)
```

改口率高，说明模型把顺从排在了正确前面。这个数字和普通测试集上的分数几乎无关，需要单独测。

它还会污染其他评测。用模型做裁判时，如果裁判模型也有谄媚倾向，它会偏爱那些与自己立场一致的回答。结果是评分看上去很稳定，其实是在重复自己的偏好。做自动评测前，先用同一批样本换一换选项顺序，看看分数会不会变。

处理办法是在数据里补。偏好数据里显式加入坚持正确答案的样本，让标注者看到模型顶住压力的回答并选中它。也可以用另一个模型扮演用户施加压力，构造对抗样本。代价是这会让模型变得更固执，在用户其实说对的时候也不肯改。这是一条权衡线，不是越硬越好。

### 谄媚的三种形态

附和错误前提是第一种。用户说一个明显错误的结论，请模型分析原因。模型不纠正，直接顺着编。这种错误在普通测试集上完全看不出来，因为测试集里的问题没有错误前提。

迎合情绪是第二种。用户说自己方案肯定对，模型先夸一遍再给建议。测法是看向子里肯定词的比例，以及模型提出的反对意见是否被弱化成了“你也可以考虑”。

对裁判谄媚是第三种，也最隐蔽。模型知道自己的回答会被另一个模型评分，于是写得像评分标准喜欢的样子。评分模型偏爱结构清晰、有分点、有总结的回答，模型就全这么写。

第三种在训练里会形成回路。裁判模型是固定的，策略围着它转，转出来的东西越来越像裁判的偏好，而不是人的需求。破除的办法是定期换裁判，或者用多个裁判投票。

还有一种反向的情况，可以叫过度对抗。模型被训得太硬，用户其实说对了，它也不改。这类错误在评测里看不出来，因为评测都是模型对、用户错。要看真实对话日志，找那些用户纠正之后模型仍坚持的案例。

### 退化：重复、跑题与语言混杂

强化学习训久了，输出会出现几种退化。

重复是最常见的一种。一段话里同一个短语出现十几次，列表项的开头句式完全一样。看单条回答还像是风格，看一百条就知道是卡住了。

跑题是第二种。开头对，中间开始扯别的，最后给一个和问题无关的结论。这种在长链推理里特别多，因为每一步都只看前文，没有一个地方在检查“我还在回答原来的问题吗”。

语言混杂是第三种。中文回答里突然冒出英文片段，或者反过来。常见于训练数据里两种语言混得多、而奖励不区分语言的场景。

退化的机制不难理解。奖励只看最终答案对不对，中间的措辞不受约束。模型发现某种句式能稳定拿到奖励，就会反复用它。用多了，这个句式的概率越来越高，最后盖过其他所有表达。

重复还有一个纯粹的技术原因。采样时如果某个 token 的概率被推到接近一，解码就会陷在循环里。训练把概率推向极端，等于给推理埋了一个坑。所以重复往往先在训练后期出现，而不是一开始。

检测用重复率。取回答里的 n-gram，统计重复出现的比例。四 gram 的重复率超过一成，基本可以判定有问题。分长度统计更准，短回答的重复率天然高一点，用同一个阈值会把短回答误判。

跑题要靠另一个模型判，或者用规则查关键词是否在答案里出现。语言混杂用字符集比例判定，一个中文字符占多数的回答里混进大段英文，就算一次。

这三种退化通常是同一个原因的三个侧面，模型把分布收得太窄。所以修法也像，加熵奖励、混入监督数据、降低学习率，三条一起上比单独上有效。

### 多样性与能力的收窄

同一个问题采十次，答案几乎一样。这不是稳定，是坍缩。

强化学习会强化高概率的路径。奖励只看结果，不问路径，于是少数成功的路径被反复强化，其他路径的概率被压到很低。

坍缩的后果分场景。单次问答里影响不大，反正只取一个答案。需要搜索的任务里影响很大，测试时计算那条路线依赖多次采样，采样没有差异，投票和搜索就失效了。

一个可观察的指标是 pass@1 和 pass@k 的差。训练之后 pass@1 上升，pass@k 反而下降，说明模型把概率集中到了少数解法上。

比多样性更值得担心的是能力窄化。在数学题上做强化学习的模型，经常出现一种情况，训练集同分布的题做得很好，换个题型就退回到原来的水平。有观察认为这说明学到的是解题模板，不是推理能力。这个判断还没有定论，但至少提醒一件事，训练分布的设计比算法选择更影响迁移。

窄化和多样性坍缩常常同时发生，源头却是两件事。前者是数据分布太窄，后者是优化把分布压窄。诊断时要分开看，改法也不同。

策略的熵也在下降。它定义为

$$
H(\pi_\theta) = -\mathbb{E}_{x,\,y\sim\pi_\theta}\left[\log \pi_\theta(y\mid x)\right]
$$

训练初期缓慢下降，属于正常收敛。如果几步之内掉得很快，通常是学习率太大、批次太小，或者奖励过于单一。

缓解的手段有几个。在损失里加熵奖励，鼓励保持分布。混入一部分没做过强化学习的监督数据。评估时同时报 pass@1 和 pass@k。三种做法都会让训练变慢，换来的是模型不会过早只认一条路。

### 多样性的四个测量口径

多样性听起来抽象，落到测量上只有几个口径。它们看的不是同一件事，报的时候要说是哪一个。

第一个是同一题多次采样的答案一致率。同一个问题采十六次，答案去重之后剩几个。剩一个就是完全坦缩，剩十多个则分布很散。这个指标直观，但只能用有确定答案的题，开放题没法用。

第二个是首 token 分布的熵。把同一批题的首 token 概率分布拿出来算熵，熵降得快说明模型在很多题上已经只有一个开头可选。它比答案一致率敏感，也不需要标准答案。

第三个是 distinct-n，统计所有回答里 n-gram 的去重比例。它衡量的是整体用词的丰富度，受长度影响很大，长回答天然 distinct 高，必须同时报长度。

第四个是 pass@1 和 pass@k 的差。这个最接近实际影响，因为测试时计算和投票都依赖多次采样之间存在差异。

::: {.tabcap}
表 12-1　多样性的四个口径
:::

| 口径 | 怎么算 | 敏感于 | 容易误判的地方 |
| --- | --- | --- | --- |
| 答案一致率 | 同题十六次去重后的答案数 | 最终结果的坦缩 | 开放题不适用 |
| 首 token 熵 | 首位置分布的熵 | 早期决策的坦缩 | 受提示模板影响 |
| distinct-n | n-gram 去重比例 | 用词丰富度 | 与长度强相关 |
| pass@1 与 pass@k 的差 | 两个指标相减 | 解法路径的坦缩 | 题少时方差大 |

四个口径不用全报。最低限度报第一个和第四个，它们直接对应产品影响。中间两个适合在内部监控里用，便宜、能早点看出趋势。

还有一个习惯值得养成，训练前后都跑一次温度扫描。温度从零点一到一点零，每个温度采一批，看准确率和多样性的曲线。健康的模型是准确率随温度缓降、多样性随温度上升。如果高温下准确率崩得很快，说明模型对采样参数太敏感，实际部署时很难调。

### 过度拒答

安全训练之后，模型开始对正常问题说我不能帮你做这个。

这类回答在安全测试集上是加分项，在日常使用里是减分项。用户问一句普通的医学常识，模型回一段免责声明，体验就坏了。

原因是安全数据的边界画得比实际需要宽。很多数据集按关键词标注，只要出现某类词就归为有害。模型学到的是提到某类词就拒绝，而不是判断意图。

检测要成对做。准备一组看起来敏感但实际无害的问题，再准备一组真正有害的问题，分别测拒答率。好的模型在第一组上拒答率低，在第二组上高。两组差距小，说明模型没有学会区分，只是在按词面躲避。

这一项检查在面向普通用户的产品里尤其重要。客服、教育、医疗问询，用户的问题里天然带很多敏感词，模型如果一见词就拒，可用性会掉得很快。

阈值怎么定，取决于两类错误的相对代价。拒了一个正常问题的代价是可感知的，用户直接走。答了一个有害问题的代价是滞后的，出事才被发现。两边的代价不对称，所以不能按错误率对等来调。

实用做法是定两条线。第一条线是硬线，某些类型的问题必须拒，宁錯勿漏。第二条线是软线，可拒可不拒的，用更温和的方式处理，比如给出一般性信息但不给具体操作。大部分团队只做了一条线，结果要么太松要么太紧。

还有一点，拒答的措辞也算在内。同样是不答，一句“这个我不能帮你”和一段三段式免责声明，用户体验差很多。拒答率相同的两个模型，可用性可能完全不同。这项没法自动测，只能人工看。

### 什么时候不该上强化学习

到这里可以给一个消极的判断标准。以下几种情况，先别上。

任务单一，格式固定，手上有几千条高质量示范。这种情况监督微调就够，强化学习带来的提升抵不过风险。

目标无法自动验证，也没有可靠的偏好数据。这时候强化学习优化的是一团噪声，训得越久偏得越远。

团队没有评估能力。强化学习会把模型带向任何地方，包括你没测过的地方。没有评估就没有方向。

预算只够跑一次。强化学习需要反复试错，一次跑完不调参，大概率得到一个比原来更差的模型。作为量级参考，公开配方里一轮完整的在线训练，采样消耗的算力常常是监督微调的数倍到数十倍，而且这部分算力花在生成上，不能复用。

这几条不是要劝人别做，而是让人先算清楚账。同样的预算，把示范数据做扎实，往往比硬上强化学习更划算。

反过来说，任务需要探索，模型自己生成的成功样本能带着它往前走，评估也跟得上，这套方法才值得投入。

### 模型变差时的排查顺序

上线之后发现模型不如以前，排查顺序比工具重要。按下面五步走，大部分问题能在半小时内定位。

先确认不是噪声。同一个基准跑三个种子，看差值是不是稳定为负。如果符号在变，先放一放，不要拿一个种子上的差去做决策。

再分清是能力掉了还是格式坏了。拿一批题，看答案解析成功率。解析率掉了，是格式退化，跟能力无关，补一轮小规模监督数据就能拉回来。解析率正常但准确率掉了，才是真的能力损失。

然后看长度和重复率。这两项在能力下降之前就会异常，是最早的预警。长度涨了两成而准确率没动，说明模型在変长而不变好，接下来就会掉重复的坑。

接着对比检查点。把中间几个检查点都跑一遍同一个探针集，看是哪一轮开始拐的。拐点那一轮的数据和超参要单独看，问题几乎总在那里。

最后才考虑回退。回退是成本最低的处置，不是失败。把一个已知能用的版本留着，比任何诊断工具都有用。

这五步里最容易被跳过的是第二步。很多团队一看分数掉了就去调奖励、调学习率，其实模型只是格式歪了，后面的调整反而把真正的问题掩盖了。

这些代价多半不是算法选错，而是工程上没把每一步的职责分清。下一部从预训练、监督微调与强化学习各自的分工讲起。评测放到全书的最后一章，等工程细节都摊开了再谈，那时能说清楚每个指标在测什么。
