## 装好一个能跑实验的环境

本书的代码都能在本机跑。一台普通的笔记本，有独立显卡更好，没有也能完成前九章的实验。

装环境这件事在过去几年变得简单了很多，但仍然是最容易卡住新手的环节。这一章把需要的东西列清楚，也给几个排错的思路。卡住的时候不用慌，多数问题来自版本不匹配，而不是你写错了什么。

### 需要的东西

四个 Python 包，加一个可选的显卡驱动。

**gymnasium** 提供标准的环境接口，CartPole（倒立摆，经典控制任务）、LunarLander（月球着陆器，Box2D 环境）这些经典任务都在里面。它是 OpenAI gym 的维护版本，接口有细微改动，网上的老代码可能需要改一行。

**torch** 用来写神经网络。装的时候注意选对版本，CPU 版和 CUDA 版是分开的包。装错了不至于报错，只是用不上显卡。

**numpy** 和 **matplotlib** 一个算数一个画图，几乎所有实验都会用到。

如果机器上有 NVIDIA 显卡，先确认驱动能用。命令 `nvidia-smi` 会打印显卡型号和驱动版本，看不到输出说明驱动没装好，这时候装 CUDA 版的 torch 也用不上。

这四个包会连带装进来一堆东西。gymnasium 依赖 numpy、cloudpickle 和 farama-notifications，torch 依赖一串 CUDA 运行时库，加起来好几个 G。这也是为什么建议单独建一个环境，装崩了直接删掉重来，比修快得多。

除了这四个，还有几个可选的东西值得知道。`tensorboard` 能把训练曲线实时画出来，跑长实验时比看终端刷屏舒服。`imageio` 用来把几帧画面拼成 gif，检查策略行为时有用。`pandas` 在汇总多组实验结果时省事。这些不装也能跑完本书，装了就少写几行代码。

### 版本怎么选

版本不是一个随便填的数字，选错了会遇到一些很奇怪的现象。

Python 建议 3.10 到 3.12。3.9 以下有些包已经不再提供预编译的 wheel，装的时候会现场编译，一编译就容易出错。3.13 太新，某些包还没跟上，尤其是需要编译的包。本书的代码在 3.12 上跑通，实测版本是这样的。

```text
python     3.12.14
numpy      2.5.2
gymnasium  1.4.0
torch      2.13.0+cu130
```

gymnasium 建议一点零以上。零点二六那次更新把接口改成了现在的样子，`reset` 的返回从单个观测变成观测加信息，`step` 的 `done` 拆成了 `terminated` 和 `truncated`。网上大量教程还是老接口，直接抄过来会报“too many values to unpack”。看到这个报错，先查版本，再改代码。

numpy 要留意二点零这个大版本。它删掉了一批用了十年的别名，`np.float_`、`np.alltrue` 这些都在被删之列。老代码在新 numpy 上会直接抛 `AttributeError`。这个问题和强化学习无关，但很多工具库的老版本会踩，报错信息看着莫名其妙。

torch 的版本要和显卡驱动对得上。CUDA 有运行时版本和驱动版本两个概念，驱动的版本必须不低于运行时。装 `cu130` 的 torch，驱动就得支持十三点零。驱动太旧时，`torch.cuda.is_available()` 会返回 False，torch 悄悄退回 CPU，训练能跑，只是慢，而且没有任何提示。这是最容易误判的一类问题，你会以为显卡坏了。

一个不严格但好用的判断方法是看 torch 的版本号后缀。`2.13.0+cu130` 说明是 CUDA 十三点零的构建，`2.13.0+cpu` 说明是纯 CPU 构建。看到 `+cpu` 就知道显卡用不上，不用再怀疑别的地方。

### 三种装法

最简单的是 conda，适合不想折腾的人。

```bash
conda create -n rlbook python=3.11 -y
conda activate rlbook
pip install gymnasium torch matplotlib
```

用 venv 也可以，和系统 Python 隔离就行。

```bash
python -m venv .venv
.venv\Scripts\activate
pip install gymnasium torch matplotlib
```

有显卡的话，torch 建议按官网给出的命令装，它会自动匹配 CUDA 版本。直接 `pip install torch` 装到的通常是 CPU 版，跑小网络没什么差别，但心理上会不踏实。

这两种方式没有本质区别，选一个顺手的就好。conda 的优势是能管非 Python 的依赖，装 CUDA 运行库时省事，代价是环境体积大、解析依赖慢。venv 轻，启动快，依赖全靠 pip，遇到需要编译的包会麻烦一些。

国内网络下 pip 常常很慢，可以换源。

```bash
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple gymnasium torch matplotlib
```

换源只影响下载速度，不影响装出来的东西。但如果某个包在镜像上版本落后，装到的可能不是最新版，这一点在跟别人对结果时要留意。

还有一种情况是机器完全离线。这时候要在有网的机器上把 wheel 下全，`pip download` 会把依赖一起下下来，然后拷过去 `pip install --no-index --find-links=./wheels`。这个流程有点笨，但在内网服务器上做实验时经常是唯一的路。

### 一台机器上放几个环境

做强化学习的人机器上通常不止一个环境。做课程作业一个，跑本书的实验一个，某个开源项目又要一套特定的旧版本。这三套依赖经常打架，尤其是 numpy 和 torch。

解法是让每个项目有自己的环境，名字起得直白一点，比如 `rlbook`、`rlbook-old`、`thesis`。激活哪个就用哪个，彼此不干扰。代价是磁盘，一个带 CUDA 的环境占好几个 G，装五个就是二十 G。现在的硬盘不太在意这个。

有一件事要注意，环境激活只在当前终端有效。开了新终端就回到默认环境，跑脚本时用错了解释器。表现是明明装了包却报没有这个模块，或者版本和刚才打印的不一样。遇到这种情况先 `where python` 看一眼，十有八九是用错环境了。

习惯上我会在项目根目录放一个 `run.bat`，里面先激活环境再跑脚本。双击就能跑，不会用错解释器。这类小脚本不优雅，但省心。

### 装完先做一次隔离检查

装完不要急着写训练代码，先确认三件事。

第一，`which python` 或 `where python` 指向的是刚建的环境，而不是系统 Python。在 Windows 上激活环境后路径里应该带环境名。这一步错了，后面的安装全白费，报错也会指向一个你根本没动过的目录。

第二，`pip list` 里有没有你不想看到的包。如果环境是从别处复制来的，可能带着一批用不上的旧包，它们会和刚装的包抢依赖。看到两个版本的 numpy 并存，基本可以判定环境脏了。

第三，装完之后把版本记下来。`pip freeze > requirements.txt` 一行就够。

```bash
pip freeze > requirements.txt
```

这份文件不只是给别人复现用。三个月后你自己回头跑同一个实验，代码没变结果却对不上，第一个要查的就是版本。有了它，至少能排除一类原因。

### 验证一下

装完跑这段，能打印出版本和显卡状态就说明通了。

```python
import gymnasium as gym
import torch

print("gymnasium", gym.__version__)
print("torch", torch.__version__)
print("cuda", torch.cuda.is_available())

env = gym.make("CartPole-v1")
obs, info = env.reset(seed=0)
print("observation", obs.shape, obs.dtype)
print("actions", env.action_space.n)
env.close()
```

正常情况下会看到观测是长度为四的向量，动作是两个。如果 `env.reset` 报错说没有 `render_mode`，检查 gymnasium 的版本，零点二六之后的接口都是现在这个样子。

### 输出怎么读

上面那段脚本的输出信息量比看上去多，值得逐行看。

`observation (4,) float32` 说明观测是一个一维的浮点数组，长度四。dtype 是 float32 而不是 float64，这一点在很多地方有影响。把观测直接塞进 numpy 做双精度运算会隐式升精度，再塞回网络又要转回来，一来一回既慢又容易出细微的不一致。

`actions 2` 是动作空间的规模。CartPole 是离散动作，取值零或一。连续动作的环境会打印出别的东西，比如 `Box(-2.0, 2.0, (1,), float32)`。

`info` 那个字典多数时候是空的，但它不是可以忽略的东西。有些环境把诊断信息塞在里面，比如这一局的总回报、步数、是否被外部打断。自己写环境时把有用的东西放进去，调试会方便很多，不用为了看一眼中间量去改环境的代码。

再往下看一层，打印空间对象本身。

```python
env = gym.make("CartPole-v1")
print(env.observation_space)
print(env.action_space)
print(env.observation_space.sample())
```

CartPole 的观测空间会打印成这样。

```text
Box([-4.8               -inf -0.41887903        -inf],
    [ 4.8                inf  0.41887903         inf], (4,), float32)
```

这行输出里有两个容易误读的地方。上下界里有 `-inf` 和 `inf`，说明速度和角速度没有硬边界，采样时会得到很离谱的值，别拿 `sample()` 的结果当真实状态的参考。角度那一维的边界是正负零点四一八八，而真正的失败阈值是正负零点二零九四，正好一半。空间边界是给采样用的宽松范围，不是任务规则。

`env.action_space.sample()` 返回的是 `numpy.int64`，不是 Python 的 `int`。多数环境能接受，个别环境会因此抛断言错误。稳妥的写法是显式转一下。

```python
action = int(env.action_space.sample())
obs, reward, terminated, truncated, info = env.step(action)
```

### GPU 检测看什么

`nvidia-smi` 的输出信息很密，实际只需要看四行。

最上面一行是驱动版本和 CUDA 版本。驱动版本要足够新，CUDA 版本是驱动支持的最高运行时版本，不是装了什么。

中间那张表是每块显卡的编号、名称、显存占用、温度和功耗。编号从零开始，多卡机器上要记住 `cuda:0` 指的是哪一块。

右下角是当前运行的进程和它们占用的显存。排查“显存不够”的问题时先看这里，经常是上一个脚本没退干净，还占着几个 G。

torch 侧的检查要多看几个字段。

```python
import torch

print("available", torch.cuda.is_available())
print("count", torch.cuda.device_count())
if torch.cuda.is_available():
    p = torch.cuda.get_device_properties(0)
    print("name", p.name)
    print("memory", round(p.total_memory / 1024 ** 3, 1), "GB")
    print("capability", p.major, p.minor)
    print("runtime", torch.version.cuda)
```

`capability` 是计算能力，比如八点九对应 Ada 架构。新版 torch 编译时会针对不同的架构生成代码，卡太老而 torch 太新时会出现“no kernel image is available”这类报错，意思是没有为你的架构编好代码。遇到这种情况只能换 torch 版本或者换卡。

还有一种更难查的情况。`is_available()` 返回 True，`device_count()` 也是一，但一跑就报 `CUDA error: out of memory`。这时候先看 `nvidia-smi` 的显存占用，如果是零却仍报显存不足，通常是驱动和运行时不匹配，或者 WSL 里的显存没有正确映射。这类问题在论坛上有大量帖子，但真正的解决办法往往就是重装驱动。

本书的脚本大多会打印一行设备信息，跑之前扫一眼，能省掉很多疑惑。

### 显卡值不值得用

本书的实验规模很小，一个四维输入、两层一百二十八的全连接网络。这种网络在显卡上跑，瓶颈不在计算，而在每一步把数据搬到显卡的开销。所以你会看到一个反直觉的现象，同一个实验在 CPU 上可能比显卡更快。

什么时候显卡才有用？网络变大、批量变大、环境变多的时候。连续动作的实验、语言模型的训练，才真正需要显卡。

代码里我留了一个开关，用环境变量控制设备。

```python
import os
import torch

def pick_device():
    if os.environ.get("RLKIT_DEVICE", "").lower() == "cpu":
        return torch.device("cpu")
    if torch.cuda.is_available():
        return torch.device("cuda")
    return torch.device("cpu")
```

跑实验时这样用。

```bash
set RLKIT_DEVICE=cpu
python run_dqn_cartpole.py
```

### 实测两组时间

上面那段说法值得用数字兜住，下面是在一台有 RTX 4090 的机器上量出来的。网络结构是四维输入、两层一百二十八、两维输出，用 Adam，只做前向、反向、一步更新。

```text
batch    CPU(ms)   GPU(ms)
    1      1.139     1.757
    8      1.161     2.157
   64      1.272     2.125
  256      1.866     2.126
```

四行数据里有三件事。

批量小的时候 CPU 明显更快，一批一条时快了一半。原因是显卡的启动开销固定，一条数据也要走一遍完整流程，而 CPU 上这点计算量根本不算什么。

显卡的耗时几乎不随批量变。从一条到两百五十六条都是两点一秒左右，说明这段时间几乎全花在固定的调度上，计算被完全掩盖了。

CPU 的耗时随批量缓慢上升，两百五十六条时升到一点九毫秒。也就是说如果批量继续加，两条曲线会交叉。交叉点在几百到一千之间，具体取决于机器和网络大小。

单独量一次前向更直观。一条观测走一遍网络，CPU 是六十六微秒，显卡是两百三十四微秒。同一个网络，显卡慢了三倍多。这不是显卡无能，而是它被当成了一条流水线来用，每次只送一个零件进去，流水线的启动时间远大于加工时间。

再看一眼环境的开销。CartPole 在一秒内能推进四万一千步，平均每步二十四微秒。也就是说一次网络前向的时间够环境走三步。在 CPU 上训练时，环境和网络的开销大致是同一量级，谁都不是压倒性的瓶颈。这也解释了为什么这类实验在小机器上完全跑得动。

真正用上显卡要等网络大到一定程度。粗略的经验是，参数量过百万、批量过千，或者同时跑几十个环境时，显卡才开始明显占优。在那之前，多花的那点时间换来的是更简单的调试过程，因为所有东西都在一块内存里，没有设备间搬运，报错也更容易看懂。

### 卡住时怎么问 AI

用 AI 帮忙排错已经是很日常的事，但提问方式决定了效率。三个经验。

第一，把完整的报错贴进去，包括最后几行的文件路径和行号。只说“跑不起来”，对方只能猜。

第二，说清楚版本。`gymnasium 0.29` 和 `1.0` 的接口有差别，`torch 2.0` 和 `2.4` 也有。把验证脚本的输出一起贴上，能省掉很多来回。

第三，要求最小复现。如果对方给了一大段代码，先让对方缩到一个能跑的最小例子，确认那个例子在你的机器上通过，再往你的代码里搬。

还有一个容易被忽略的点。AI 给出的代码经常是“看起来对”的，尤其是强化学习这种带随机性的代码，跑起来不报错但学不会，很难一眼看出问题。所以每次改动之后，先用小的回合数跑一遍，看曲线有没有动静，再决定要不要加长训练。

如果要更省事，可以把版本信息做成一段可以直接粘的文本。

```python
import platform
import sys
import gymnasium as gym
import numpy as np
import torch

print(platform.platform())
print("python", sys.version.split()[0])
print("numpy", np.__version__, "gymnasium", gym.__version__)
print("torch", torch.__version__, "cuda", torch.cuda.is_available())
```

这段输出贴进对话，对方能立刻排除一整类问题。

### 六个真报错

下面六条都是实际跑出来的，不是编的。放在一起看，会发现它们全都指向同一个方向，接口变了或者类型不对，而不是算法写错了。

::: {.tabcap}
表 1-1　动手时最常撞上的六个报错
:::

| 报错 | 触发写法 | 原因与处理 |
| --- | --- | --- |
| `ValueError: too many values to unpack (expected 4)` | `obs, r, done, info = env.step(a)` | 新版 step 返回五个值，按五个接 |
| `AssertionError: array([1]) (<class 'numpy.ndarray'>) invalid` | `env.step(np.array([1]))` | 动作要标量，补一个 `int(...)` |
| `AssertionError: 5 (<class 'int'>) invalid` | `env.step(5)` | 动作越界，CartPole 只有零和一 |
| `AttributeError: np.float_ was removed in the NumPy 2.0 release` | 老代码里的 `np.float_` | 换成 `np.float64`，或降 numpy |
| `ModuleNotFoundError: No module named 'gym'` | `import gym` | 包名已改为 gymnasium |
| `ResetNeeded: Cannot call env.render() before calling env.reset()` | 未 reset 就渲染 | 先 reset，再 render，并设 `render_mode` |

第一条最容易遇到。网上抄来的训练循环几乎都是四元组，运行就崩。它不会给你任何提示说接口变了，只会说你解包的数量不对。

第二条的诱因是自己写的代码里动作变成了数组。比如从网络输出取动作时写成 `action = logits.argmax()`，得到的是一维张量，转成 numpy 后形状是 `(1,)`。加一层 `int()` 就解决了。这类错误在 CartPole 上会立刻暴露，环境做断言检查，其实算是好事，有些环境不检查，直接拿到一个奇怪的结果，更难查。

第三条通常是动作来自 `np.argmax` 之外的来源，比如自己算了个索引越界，或者动作数搞错了。写代码时用 `env.action_space.n` 而不是硬编码，能少一半这类问题。

第四条和强化学习无关，纯粹是 numpy 二点零的清理。旧教程里到处是 `np.float_`、`np.bool8`。批量替换成 `np.float64` 和 `np.bool_` 就好。

第五条在照抄老教程时出现。`gym` 和 `gymnasium` 是两个包，装了后者不会让前者可用。

第六条只在想看看画面时出现。新版要求先给 `render_mode`，并且必须 reset 之后才能渲染。想省事就用 `render_mode="rgb_array"`，拿到数组自己存图，不用开窗口。

### 排查的顺序

报错的时候别急着一行行读代码，按下面的顺序走，多数问题三步之内能定位。

先看报错类型。`ModuleNotFoundError` 和 `ImportError` 是环境问题，`AssertionError` 和 `ValueError` 多半是接口用错，`RuntimeError` 涉及张量形状或设备，`AttributeError` 常是版本差异。类型决定了往哪个方向查。

再看报错位置。如果栈的最后一行在你的代码里，那就是你的问题。如果全在库的内部，往上找到第一个属于你的调用，问题往往在那一行的参数上。

最后看能不能缩到十行以内。十行能复现的问题，把十行贴出去问；十行不能复现，说明问题藏在别处，先把它找出来。

有三类问题不看报错就能排除。版本对不上，用验证脚本一跑就知道。显卡没被用上，看 `torch.cuda.is_available()` 和 `nvidia-smi` 就够。数据形状不对，打印一次 `obs.shape`、`action.shape` 就清楚。

### 一次装崩的复盘

讲一个真实的例子，因为它把上面几条都串起来了。

那天想跑一个别人的 DQN 实现，仓库里给的是 `requirements.txt`，我图省事直接在一个用了半年的环境里装上。装的过程一切正常，跑起来第一行就报错，说 `np.float_` 不存在。降了 numpy 到一点二六，那个错没了，换成 torch 报版本冲突，说编译时的 numpy 接口和运行时不一致。再降 numpy，gymnasium 又不认这个版本。

来回折腾半小时才想明白，问题不在于哪个版本对，而在于这个环境里已经有一堆包依赖着不同的 numpy。正确的做法是建一个新环境，只装这个仓库要求的包，装完再按版本表核对一遍。三分钟解决。

这件事的教训很直接。环境脏了不要修，直接扔。修一个装了半年的环境，你永远不知道哪个包在背后拽着另一个包。新建一个环境的成本是几分钟，修的成本是几个小时，而且修完之后你也不敢保证它是干净的。

### 本书的目录

代码放在书的仓库里，按实验分文件。

```text
books/code/hands-on/
├── rlkit.py              公用工具：随机种子、设备、评估、结果保存
├── gridworld.py          自己写的网格世界
```

每个脚本都能单独跑，跑完把结果写进 `results/`，插图脚本再从那里读数据。这样图和代码是分开的，改图不用重跑实验，改实验也不用动图。

目录里还有一层 `chNN` 子目录，每个放一章的插图脚本。这些脚本都很短，读数据、画图、保存，二十行左右。想改图的样式，改这里就够了，不用碰训练代码。

### 结果放哪，怎么核对

`results/` 里的文件一律是 JSON，一个实验一个文件，文件名带上关键配置。比如 `dqn_lr0.0001_s0.json`，一眼能看出是学习率零点零零零一、种子零的那次。

文件名里带配置有一个好处，同一个脚本反复跑不会互相覆盖，也不会因为改了参数而把旧结果冲掉。坏处是文件会越来越多，跑几十组之后目录就没法看了。我通常按章节再分一层，跑完一组就挪进去。

结果文件里除了曲线，还存了配置和几个汇总指标。

```python
import json
from pathlib import Path

path = Path("results/dqn_vanilla_s0.json")
data = json.loads(path.read_text(encoding="utf-8"))
print(data["config"])
print(len(data["returns"]))
```

养成先看 `config` 再看曲线的习惯。很多“结果对不上”的情况，其实是配置不一样，比如一个跑了五百回合另一个跑了三百，或者探索率不一样。先核对配置，能省下大量时间。

还有一个小习惯值得一提。每跑完一组实验，把当次的命令和一句话结论记在一个文本文件里。过两周回头看曲线，你会想不起来这条平滑的线是哪组参数。一句话的记录比任何命名规范都可靠。
