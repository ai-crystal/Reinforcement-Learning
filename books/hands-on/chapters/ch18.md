## 保存、回放与部署

训练跑完，模型在内存里，程序和它一起结束，什么都不剩。

这一章讲三件事，把训练好的策略存下来，把它跑起来看效果，以及把它接进一个真实程序时要注意什么。

### 存什么

PyTorch 的模型参数用 `state_dict` 保存，不要用 pickle 整个对象。前者只存参数，加载时不依赖原来的类定义位置，后者换个目录就可能报错。

```python
torch.save({
    "model": q.state_dict(),
    "config": {"obs_dim": 4, "n_actions": 2, "hidden": 128},
    "seed": 0,
    "episode": 250,
}, "cartpole_dqn.pt")
```

除了参数，把结构信息和训练信息一起存下来。加载时先按配置重建网络，再灌参数。

```python
ckpt = torch.load("cartpole_dqn.pt", map_location="cpu")
q = QNet(ckpt["config"]["obs_dim"], ckpt["config"]["n_actions"])
q.load_state_dict(ckpt["model"])
q.eval()
```

`eval()` 这一行容易漏。它会把 dropout 和批归一化切到推理模式。这个小网络的代码里可能没有这两层，但养成习惯，换一个网络就不会出错。

### 跑起来看

存完不等于能用。先写一个最简单的推理循环，确认它真的会做事。

```python
obs, _ = env.reset(seed=123)
done, total = False, 0
while not done:
    with torch.no_grad():
        z = torch.as_tensor(obs, dtype=torch.float32)
        action = int(q(z).argmax().item())
    obs, reward, term, trunc, _ = env.step(action)
    total += reward
    done = term or trunc
print("return", total)
```

这段和训练时的评估一模一样，区别是没有探索，也没有更新。跑几局，看回报是不是和训练时的评估接近。差很多，说明保存或者加载的环节出了问题。

### 录下来

想直观看到策略在做什么，可以把画面存成图片序列。

```python
env = gym.make("CartPole-v1", render_mode="rgb_array")
obs, _ = env.reset(seed=123)
frames = []
done = False
while not done:
    frames.append(env.render())
    action = int(q(torch.as_tensor(obs, dtype=torch.float32)).argmax())
    obs, reward, term, trunc, _ = env.step(action)
    done = term or trunc
```

`frames` 里是一张张 RGB 数组，可以用 imageio 或者 PIL 存成 GIF。这一步需要装 `pygame`，因为 gymnasium 的渲染依赖它。没装的话，`render_mode="rgb_array"` 会报错。

录制的价值在于看失败模式。回报数字只能告诉你"这一局得了两百分"，看不清它是在哪一步开始晃的。慢放一遍，问题往往一眼就能看出来。

### 接进真实程序

把策略接进一个程序，和跑评估脚本有几处不同。

输入要一致。训练时的观测顺序、归一化方式，推理时必须完全一样。少做一步归一化，策略的表现就会莫名其妙地下降。

动作要裁剪。网络输出的是原始值，真实设备有物理限制。超出范围的动作要截断，不能直接下发。

要有人工兜底。策略在训练分布内可靠，出了分布可能做出奇怪的事。加一个规则层或者一个急停开关，代价很小。

要有监控。记录每一步的观测、动作、奖励，出问题时才有据可查。

### 一个部署检查清单

上线之前，逐条确认。

模型文件和配置一起打包了吗。

推理时的观测处理和训练时一致吗。

动作的数值范围处理了吗。

超时和异常有兜底吗。

有没有一个回放或者日志，能在出问题时复现。

这五条都过了，才算真的"能用"。多数失败不是算法不行，而是这几步里漏了一步。
