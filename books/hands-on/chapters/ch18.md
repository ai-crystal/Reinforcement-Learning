## 保存、回放与部署

训练跑完，模型在内存里，程序和它一起结束，什么都不剩。

这一章讲三件事，把训练好的策略存下来，把它跑起来看效果，以及把它接进一个真实程序时要注意什么。

### 存什么

PyTorch 的模型参数用 `state_dict` 保存，不要用 pickle 整个对象。前者只存参数，加载时不依赖原来的类定义位置，后者换个目录就可能报错。

```python
torch.save({
    "model": q.state_dict(),
    "config": {"obs_dim": 4, "n_actions": 2, "hidden": 128},
    "seed": 0,
    "episode": 250,
}, "cartpole_dqn.pt")
```

除了参数，把结构信息和训练信息一起存下来。加载时先按配置重建网络，再灌参数。

```python
ckpt = torch.load("cartpole_dqn.pt", map_location="cpu")
q = QNet(ckpt["config"]["obs_dim"], ckpt["config"]["n_actions"])
q.load_state_dict(ckpt["model"])
q.eval()
```

`eval()` 这一行容易漏。它会把 dropout 和批归一化切到推理模式。这个小网络的代码里可能没有这两层，但养成习惯，换一个网络就不会出错。

### 存参数还是存整个对象

两种存法都能用，但只有一种经得起时间。

整个对象存下去（直接 `torch.save(model)`）看起来方便，它把类名、模块路径、参数一起序列化。问题是这些信息对环境敏感。你把训练脚本从一个目录搬到另一个，或者把类从 `train.py` 拆到 `model.py`，加载时就会找不到类，报一个看着莫名其妙的错。

`state_dict` 只存一串张量字典，加载时你得自己建网络、自己 `load_state_dict`。多写两行，但这两行就是“结构描述”，写明了一个检查点属于什么形状的网络。换一台机器、换一个目录、甚至换一个深度学习框架版本，只要结构一致就能加载。

还有一个更实际的理由，可审计。`state_dict` 是纯数据，人能看懂它有多少层、每层多大。整个对象存下来之后，里面混了代码信息，出了问题很难定位是数据错还是代码错。

代价是加载时需要重建网络。所以**结构参数必须和参数一起存**，不能只存权重。这是一个常犯的错，存的时候觉得“结构写在代码里就行了”，几周后发现代码改过了。

### 跑起来看

存完不等于能用。先写一个最简单的推理循环，确认它真的会做事。

```python
obs, _ = env.reset(seed=123)
done, total = False, 0
while not done:
    with torch.no_grad():
        z = torch.as_tensor(obs, dtype=torch.float32)
        action = int(q(z).argmax().item())
    obs, reward, term, trunc, _ = env.step(action)
    total += reward
    done = term or trunc
print("return", total)
```

这段和训练时的评估一模一样，区别是没有探索，也没有更新。跑几局，看回报是不是和训练时的评估接近。

别只跑一局。存盘和加载的错往往只在某些初始局面上暴露，比如杆子一开始就斜得很厉害的局。跑上二十局，看最低的那几局，比看平均更能发现问题。差很多，说明保存或者加载的环节出了问题。

### 检查点存几份

训练一小时的任务，存一份就够；训练一天的任务，存一份很危险。

常见的做法是三份。`last.pt` 每次都覆盖，保证中断时能接上。`best.pt` 只在评估刷新时写，用来选最终模型。`every_100.pt` 每百局一份，作为回溯点。

三份加起来占的空间往往比想象的小，因为 DQN 这种小网络的参数量只有几十万，一份几百 KB。图像任务的参数量大一些，一份几十 MB，几百个检查点就开始占盘了，这时候要按时间而不是按局数来留。图像任务才需要认真考虑磁盘，比如只保留最近五个和最好的一个。

选 `best.pt` 的时候要注意一点，评估本身有噪声。用一个种子评五局，分数波动很大，导致 best 在两个差不多的模型之间来回切。更稳的做法是存“最后一段的滑平均最高”而不是“单次最高”。

### 录下来

想直观看到策略在做什么，可以把画面存成图片序列。

```python
env = gym.make("CartPole-v1", render_mode="rgb_array")
obs, _ = env.reset(seed=123)
frames = []
done = False
while not done:
    frames.append(env.render())
    action = int(q(torch.as_tensor(obs, dtype=torch.float32)).argmax())
    obs, reward, term, trunc, _ = env.step(action)
    done = term or trunc
```

`frames` 里是一张张 RGB 数组，可以用 imageio 或者 PIL 存成 GIF。这一步需要装 `pygame`，因为 gymnasium 的渲染依赖它。没装的话，`render_mode="rgb_array"` 会报错。

录制的价值在于看失败模式。回报数字只能告诉你"这一局得了两百分"，看不清它是在哪一步开始晃的。慢放一遍，问题往往一眼就能看出来。

### 回放能看出什么

看回放的时候，心里要先有几个典型形状，否则很容易只看到“它在动”。

第一种是拖。小车和杆子在临界位置来回磨，每一步都在微调而不往前走。这种模式往往意味着价值函数的尺度偏小，或者 epsilon 没有退干净。

第二种是卡。在某个位置上不动，无论怎么走都回到这个位置。这看起来像是死循环，实质是策略在一个很小的循环里振荡。把它与探索关掉的画面对一下，如果关探索之后就不卡了，那就是探索残留。

第三种是猛。开局一两步就做出极大的动作，然后直接失败。这种通常是动作没裁剪，或输出层初始化太大。

第四种是“会但很粗”。能完成，但每一步都是大动作，哐哐哐地碰。这种在离散化任务上最常见，指的是档位太粗，策略只能在少数几个极端值里选。

录的时候有几个实用细节。录三到五局不同种子的，不要只录一局。加上真分数显示，否则看不出哪一帧是关键。帧率不要太低，CartPole 一局最多五百步，按每秒三十帧存，一局就是十几秒，刚好能看完。

### 接进真实程序

把策略接进一个程序，和跑评估脚本有几处不同。

输入要一致。训练时的观测顺序、归一化方式，推理时必须完全一样。少做一步归一化，策略的表现就会莫名其妙地下降。

动作要裁剪。网络输出的是原始值，真实设备有物理限制。超出范围的动作要截断，不能直接下发。

要有人工兜底。策略在训练分布内可靠，出了分布可能做出奇怪的事。加一个规则层或者一个急停开关，代价很小。

要有监控。记录每一步的观测、动作、奖励，出问题时才有据可查。

这四条之外还有一条很容易被忽略，策略的时间尺度。训练时一局几百步，你可能不在意前面几十步的延迟；上线后每一步都有硬性时限，迟到的决策等于错的决策。所以在接入层要明确一件事，决策超时的时候给什么动作。给上一个动作、给零动作、还是交给规则层，三种选择都要提前定下来，不能留给运行时随机。

### 断点续训要恢复什么

训练跑到一半被打断，接上去比从头再跑一下省钱。但“接上”要恢复的东西比多数人想象的多。

模型参数是必须的。优化器状态也是必须的，Adam 里存了每个参数的动量和方差，不恢复的话前几步相当于重新热身，曲线会有一个小坑。步数是必须的，因为 epsilon 衰减、目标网络同步、学习率调度全靠它算。随机数状态也是必须的，否则探索路径和填池子的数据全变了。

```python
ckpt = {
    "model": q.state_dict(),
    "target": target.state_dict(),
    "opt": opt.state_dict(),
    "step": step,
    "episode": ep,
    "rng": rng.bit_generator.state,
    "torch_rng": torch.get_rng_state(),
    "config": cfg,
}
```

回放缓冲区默认不存。它可能几万条，存下来文件巨大，而且重新填满只要几百局。代价是继续训练之后，前一段的经验没了，初期会有一点扰动。对短任务这笔交易划算，对样本极贵的任务就不一定。

续训最常见的现象是“曲线接不上”。前三局明显偏高，然后又回落。原因通常就是优化器状态或随机数没恢复。判断办法很简单，再存一次、再加载一次，看能不能重复出同一个数字。

### 加载失败的三种报错

第一种，`Missing key(s) in state_dict`。意思是网络里有层没被赋值，常见于结构参数不一致。比如训练时用了 bias，加载时 `bias=False`。这种报错很友好，因为它列出了缺哪些。

第二种，`size mismatch for ...`。形状对不上，通常是 `obs_dim` 或 `n_actions` 记错了。比如训练时动作数是二，加载时按四建的网。

第三种，`PytorchStreamReader failed` 或者直接失败。文件本身坏了，多半是保存时程序被强行终止，写了一半。这就解释了为什么保存要用“先写临时文件再改名”的方式。

```python
tmp = path.with_suffix(".tmp")
torch.save(ckpt, tmp)
tmp.replace(path)
```

这三行能避免大多数文件损坏。区别很小，但在训练八小时、存盘时断一次电的场景里，它救你的整晚。

### 推理时的四处不一致

部署之后表现变差，九成是某一处和训练时不一样。四处按可能性排序。

观测。训练时用的顺序、单位、归一化方式，推理时必须一模一样。最常见的是“训练时用了均值方差归一化，推理时忘了”。这种错很难发现，因为策略不会崩，只是变差。

动作。训练时的动作是离散索引或连续数组，推理时的接口可能要求不同的类型或形状。前面讲过的“整数传给连续动作空间”就属于这一类。

模式。`model.eval()` 没调用，`torch.no_grad()` 没用，这两件在单次推理里影响很小，但会在高频推理时把内存吃满。

线程。推理服务往往多线程，而训练是单线程。如果网络里有任何隐式状态，多线程会出错。最简单的办法是给推理进程加一个锁。

### 上线前的一次演练

不要第一次上线就去碰真设备。先做一次离线演练。

找一个和现场相近但安全的场景，把整套流程跑一遍。包括启动、读模型、循环推理、超时处理、日志写入、退出。计时每一步，看总延迟是不是在预算内。

演练时要故意制造三种异常。观测里出现 NaN，动作接口超时，模型文件缺失。看程序是不是能安全地停下来，而不是卡在半路。

这一步花半天，能抵掉上线后一周的兵慌马乱。

### 推理延迟与预算

训练时你关心“学得好不好”，上线后你关心“来不来得及”。这两件事的衡量方式完全不同。

一个四维输入、两层一百二十八的 DQN，前向一次在 CPU 上大约二十微秒，看上去很快。但如果你的控制循环要跑一百赫兹，那就是每十毫秒一次决策，这个预算里还得包含读传感器、算特征、下发指令、等执行器响应。留给策略的可能只有一毫秒。

测试的方法不是算，是量。在目标机器上跑一万次推理，计时。把模型加载、输入预处理、前向、后处理分开计时，才知道哪一段占了大头。很多时候前向只占一成，剩下的都是预处理。

计时的第一个坑是预热。第一次推理要分配内存、初始化线程池，耗时是后面的几十倍。把前一百次丢掉，从第一百零一次开始计。第二个坑是Python 的循环本身。一万次纯循环也要几毫秒，测出来的数字里含着这部分。要么扣掉，要么用一个已知耗时的空函数对比一下。

如果延迟超预算，有三个不花钱的办法。把网络剪小，宽度减半往往只损失一点效果。把动作缓存，状态变化很小时直接重用上一个动作。降低决策频率，比如每三步决策一次，中间用规则补。

最后一个办法不优雅，但在很多控制场景里真的有用，因为它把计算预算从“每步一次”变成了“每三步一次”。

### 什么情况下不该用强化学习

部署一章里提这个看起来奇怪，但它能省下你很多时间。

如果你能用规则写清楚，就写规则。温度控制、简单的避障、固定的流水线调度，规则往往更可靠、可解释、好调。强化学习适合的是“规则写不出来但你能量化好”的任务。

如果你的环境会变。策略是在一个分布上训的，环境一变分布就变了。如果变化不频繁，可以定期重训；如果每次都不一样，那你要的不是一个策略，而是一个自适应系统。

如果你需要事前保证。强化学习策略没有“不会撞墙”这种保证，它只是在训练分布上统计意义上很少撞。安全要求高的场合，需要的是规则层、限制层、监控层，策略只是其中一块。

如果你没有评估手段。上线的第一步不是部署，是确定“怎么知道它做得对”。没有这个，部署之后的所有判断都是猜。

### 一个部署检查清单

上线之前，逐条确认。

模型文件和配置一起打包了吗。

推理时的观测处理和训练时一致吗。

动作的数值范围处理了吗。

超时和异常有兜底吗。

有没有一个回放或者日志，能在出问题时复现。

这五条都过了，才算真的"能用"。多数失败不是算法不行，而是这几步里漏了一步。下面这张表把每条检查项和验收方式放在一起，发布前从上往下过一遍就行。

### 监控看哪几个数

上线之后，不是“能跑”就完了。你要能看到它在变差，而且要在变差得还不严重时看到。

四个数比较关键。第一个是每局回报，它是最终结果；第二个是每局长度，它能区分“做得差”和“快速结束”；第三个是观测的分布，比如每一维的均值和最大值，它能提前告诉你环境变了；第四个是动作分布，如果突然集中在某一个值，说明策略卡住了。

四个数里最有用的是第三个。回报变差是滞后信号，观测分布变才是超前信号。比如传感器慢慢偏移，回报可能要一周后才掉，但观测均值当天就会变。

记录的方式很土但有效，每小时一个统计行，存成 jsonl。不需要可视化，需要时再画。

### 版本与回滚

策略文件也要有版本号。这不是形式主义，出事的时候它能救你。

建议的命名方式是算法、训练日期、短暂标记，比如 `dqn_20260302_a3f1.pt`。同时保留一份当前使用的版本指针，一个只有一行字的文本文件，里面写当前加载哪一个。

回滚的流程要提前演练。旧版本还在，配置文件指向它，重启服务，三个动作。如果只测了“切换新版本”，没测“切回去”，那你在真出问题时没有退路。

还有一件容易忽略的事，配置回滚和数据回滚要一致。如果新旧两版的观测归一化不同，单独回滚模型文件会让输入不匹配。所以模型、配置、预处理代码要作为一个整体版本管理。

### 一个真实的上线问题

最后一个例子，它几乎包含了本章的所有要点。

现象是这样。一个在仿真里能稳定运行的 CartPole 策略，接到一个外部控制程序里之后，前几秒正常，十秒后开始振荡，最后倒下。

第一嫌疑是模型坏了。把同一份权重拿回评估脚本跑，五百步满分。模型没问题。

第二嫌疑是输入。把外部程序每一帧的观测打出来，与仿真里的对照，发现位置的单位差了一百倍。仿真里是米，外部程序里是厘米。策略把“位置零点一米”看成了“位置十米”，于是拼命往回拉。

这一条正好对应本章第一节说的“输入要一致”。它不是算法问题，是一个单位换算。

第三个发现更麻烦。即便单位改对了，策略在长时间运行后仍然会慢慢偏。原因是外部程序传过来的角度没有归一化到正负派，转几圈之后变成了一百多弧度。策略从来没见过这么大的角度。

两个修法。在接入层把角度归一化，这是一行代码。或者在训练时就把观测做同样的归一化，让策略见过这些值。两个都做最安全。

这件事的教训是，部署的难点不在网络，在两边的接口。所以上线前的演练要拿真实数据跑，不要用仿真数据跑，因为仿真数据本身就已经在“正确的那一侧”了。

### 把检查写成脚本

清单靠人是守不住的，跑三次就会跳步。把能量化的项写成一个小脚本，每次发布前跑一遍。

脚本做四件事。加载一次模型，跑一局固定种子的评估，把结果和一个基准对比，最后打印一个通过或不通过。

```python
def smoke_test(ckpt_path, baseline_return, tol=0.1):
    ckpt = torch.load(ckpt_path, map_location="cpu")
    q = QNet(ckpt["config"]["obs_dim"], ckpt["config"]["n_actions"])
    q.load_state_dict(ckpt["model"])
    q.eval()

    env = gym.make("CartPole-v1")
    score = evaluate(env, lambda o: int(q(torch.as_tensor(o, dtype=torch.float32))
                                       .argmax().item()), episodes=20, seed=1234)
    ok = score >= baseline_return * (1 - tol)
    print("score %.1f baseline %.1f -> %s" % (score, baseline_return,
                                              "pass" if ok else "fail"))
    return ok
```

这个脚本不保证策略好，但它能接住九成的“打包漏了一个文件”和“预处理改了忘了改回去”。成本是几十行代码，收益是每次发布不再靠手感。

### 什么情况下该重训

策略不是一次上线就永远能用。有三种情况该重新训练。

环境变了。硬件换了、传感器的偏差变大了、任务的成功标准变了。前两种可以从监控里的观测分布看出来，第三种得人判断。

数据分布变了。训练时的起始状态和现在的不一样，比如原来从静止开始，现在从运动中开始。这种变化最难发现，因为回报不会马上掉，但成功率会慢慢降。

策略被规则层接管了。如果你的兜底规则频繁触发，说明策略在很多情况下已经不可信了。这时应该把那些情况加进训练数据。

重训时不要直接覆盖旧模型。先并行跑一段时间，用同一套监控对比两者，确认新的确实更好再切。这个流程不新鲜，但能避免很多麻烦。

还有一件事值得写在部署文档里，回放数据保留多久。出问题时你需要的往往是两周前的数据，而默认的日志轮转可能只留三天。保留周期、存储位置、怎么取回，这三件事提前写清楚，事到临头就不会手忙脚乱。
